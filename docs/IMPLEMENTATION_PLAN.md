# ORBITO Personal Jarvis — Implementation Plan

**Product target:** a powerful, local-first, single-user assistant on the owner's
Windows PC. The primary loop is **listen → understand → propose/act safely →
report by text or speech**. The app should feel capable because real actions work,
not because the dashboard claims that they do.

This plan supersedes the multi-user-first sequencing in `ROADMAP.md` and older
blueprint documents. `ARCHITECTURE.md`, `SECURITY.md`, `AGENTS.md` and the
OpenCode skills define the engineering constraints. Update the code status here
only after verifying it.

## Product decisions

- Optimize for one trusted operator and one Windows workstation. Do **not** build
  registration, billing, tenant RLS or a cloud control plane before the personal
  assistant loop is useful.
- Run desktop-control code natively in the logged-in Windows session. Docker or
  WSL cannot reliably control the user's interactive desktop; they remain
  optional for infrastructure, never the desktop executor.
- Keep the API on loopback (`127.0.0.1`) while desktop tools are enabled. LAN or
  remote control is a separate security project and stays disabled by default.
- The model may propose a typed tool call; only the server-side registry,
  validators, permission policy and approval service may execute it. Prompts are
  not security controls. No model-generated shell, PowerShell, Python, URLs to
  arbitrary executables, or free-form input injection on the host.
- Start with deterministic, inspectable schemas and a small tool set. Use model
  tool calling only after the exact local model/provider combination is tested;
  keep a safe fallback when tool calling is unavailable or malformed.
- Local-first is a routing preference, not a claim that every call is local.
  Show the resolved provider/model and clearly label any cloud fallback.
- Never fabricate PC state, news locations, memory, tool success or voice
  transcripts. Missing permission, unsupported hardware and unavailable feeds
  must be visible.

## Current baseline (verified 2026-11-08)

- Web app, FastAPI API, SQLite, local Ollama, Model Hub, chat history, memory
  CRUD, news/markets and the Three.js Planet page exist.
- Ollama was reachable from the local API health endpoint. Confirm the provider
  and model on a real chat/task trace at the start of a PC-control sprint; health
  alone does not prove the answer was generated by Ollama.
- Existing agents are keyword-routed. The orchestrator calls an agent gather
  method once and then generates a response; **general schema-based model tool
  calling is not implemented**.
- Current registered tools cover web search, browser, documents, workspace
  filesystem and a non-executing delete placeholder. **There are no Windows
  desktop-control tools.**
- Tool permission levels and policy exist, but **there is no reliable end-to-end
  approval queue/execution gate yet**. Treat all sensitive actions as blocked.
- Memory CRUD and bounded recall are present. Semantic embeddings/RAG are not.
- `/voice` is a page shell. There is no STT, TTS, push-to-talk capture or wake
  word implementation.
- The Planet has local 4K surface textures and live publisher headlines. It is a
  secondary product surface, not a prerequisite for Jarvis.
- Windows verification is mandatory. Linux-only assumptions have previously
  caused failures (`/proc`, `num_fds`); do not call a feature done based on Linux
  CI alone.

## Build order

### Phase 0 — Prove the local runtime (short verification gate)

- [ ] Run Ollama and confirm installed models with the Model Hub / `ollama list`.
- [ ] Send a real chat request and inspect its task/model trace and usage record:
      verify provider is Ollama and the resolved model is the intended fast role,
      not `mock` or an unexpected cloud fallback.
- [ ] Check API health, database, web app, Windows process/system data and local
      model memory usage. Record unsupported values as unavailable.
- [ ] Verify the local dev API is bound to `127.0.0.1`; document any service
      listening on non-loopback interfaces before enabling desktop actions.
- [ ] Keep the first command model small/fast; benchmark before selecting a
      reasoning model for routine control.

**Done when:** a task trace proves local Ollama generated the response and the
Windows system view reports real measurements or explicit unavailable values.

### Phase 0.5 — Integrated Project Task Manager ✅

The planning surface is now inside ORBITO. It is a Jira-style project board,
separate from the agent execution monitor.

- Project work items live in `project_work_items`; agent executions remain in
  `tasks` / `task_events`.
- Kanban columns: backlog, to do, in progress, blocked and done; create/edit,
  search, priority, labels, estimates, due dates and local-calendar scheduling.
- A next-day plan surfaces tasks scheduled for tomorrow. “Run with ORBITO” opens
  Chat and links the real execution ID back to that project card.
- A model answer/completed run does not automatically mark a project item done;
  the user decides when the work itself is complete.
- Records use the configured `DATABASE_URL`. SQLite remains zero-setup;
  PostgreSQL can run locally or through the optional Docker Compose database.
  No seed/demo work items are inserted.

**Done when:** board CRUD/status changes, daily plan, database persistence and
Chat execution linking pass API tests. (Implemented; browser and configured
PostgreSQL acceptance still need verification.)

### Phase 1 — Safety spine: local identity, approvals and audit (first build)

Do this **before** adding tools that change desktop state.

- [ ] Replace advisory-only permission checks with an enforced server-side
      policy at the final execution boundary. Deny by default for unknown tools,
      invalid arguments, missing approval, expired approval and policy errors.
- [ ] Add a minimal single-user approval store/API/UI. A pending action displays
      the exact action, target, arguments/diff, originating request and risk.
      Support approve once, reject, expire and cancel; no blanket approval for
      destructive actions.
- [ ] Bind approval to an immutable normalized action payload, user session,
      task, tool and short expiry. Revalidate the payload and policy at execution
      time; prevent replay and duplicate execution.
- [ ] Persist an append-only task/audit event for proposal, approval decision,
      execution start, result/failure and cancellation. Redact secrets and
      clipboard/screenshot contents.
- [ ] Establish local-only deployment guard: loopback bind, strict CORS/origin
      checks, no wildcard LAN exposure. Desktop tools refuse to run if the
      process is not on Windows or API access is not local.
- [ ] Protect settings/approval endpoints against browser-origin abuse. Treat
      local web pages and browser extensions as untrusted; do not assume
      "localhost" alone authenticates a request.
- [ ] Add a kill switch to disable all PC-control tools immediately.

**Done when:** integration tests prove an unapproved action never executes, a
modified/replayed approval is rejected, each decision is auditable, and a local
user can approve/reject from the UI. Until then, do not wire approval-class tools
into the runtime.

### Phase 2 — Windows PC tools: small, reliable and observable

Implement tools in `apps/api/app/tools/` behind typed schemas, an explicit
registry and the Phase 1 policy. Run natively in the user's Windows session.

#### Initial read-only / low-risk tools

- [ ] `get_system_status`: OS, CPU/RAM/disk and Ollama state from real sources.
- [ ] `search_files`: bounded search only inside configured, user-approved roots;
      skip secrets, system folders, reparse-point escapes and huge files.
- [ ] `screenshot`: explicit user request only; process locally, show preview,
      never retain by default, redact from logs. Require opt-in because a screen
      can contain private information.
- [ ] `open_app`: launch a named executable from an administrator/user-managed
      allowlist. The model supplies an app ID, never an arbitrary command/path.
- [ ] `open_url`: user-visible browser launch, allow only `http`/`https`, block
      credentials and dangerous schemes. Ask before opening if the model inferred
      rather than the user explicitly requested the URL.
- [ ] `set_volume` / `media_control`: bounded OS media actions (volume 0–100,
      play/pause/next/previous), with current state where the OS supports it.
- [ ] Clipboard read is **not** silently available to every agent. Make it a
      separate opt-in tool, explicit-request only, no persistence, with UI warning.

#### Approval-required / restricted actions

- [ ] File write, move, overwrite and delete: always preview exact paths/content
      and require one-time approval. Never allow paths outside configured roots.
- [ ] Close/terminate an application: show process name/PID and require approval;
      protected process blocklist and PID revalidation required.
- [ ] Keyboard typing, clicks, macros and other UI injection: approval for every
      bounded action or short, user-started session. Use accessibility/UI
      automation IDs where possible; do not rely on blind coordinates by default.
- [ ] Shell/process launch: **no arbitrary shell**. If later needed, expose only
      named, fixed-argument actions from a code-owned allowlist; validate every
      argument, executable path, cwd, timeout and output cap. Mark restricted and
      require explicit user initiation/approval. Never execute model-produced
      PowerShell, CMD, Python or scripts.

- [ ] Add per-tool timeout, cancellation, structured result, task trace and
      Windows-specific unit/integration tests using fake adapters where possible.
- [ ] Ensure the API/web remain usable when desktop access is unavailable or
      denied; expose capability state instead of returning fake success.

**Done when:** the first five user flows (open an allowlisted app, open a URL,
set volume, find a file, capture a requested screenshot) work on Windows, produce
visible traces, and pass approval/denial/path/policy tests. No destructive or
input-injection tool is enabled without its approval test.

### Phase 3 — Real model tool calling (bounded agent loop)

- [ ] Extend the model gateway contract to represent typed tool definitions and
      tool-call stream events. Keep provider-specific formats inside each
      provider adapter.
- [ ] Verify Ollama + the configured local model can emit valid structured tool
      calls. Add a recorded fixture/test and a live manual acceptance test; do
      not assume that a model family supports every tool-call format.
- [ ] Orchestrator loop: model proposes → validate schema → authorize policy →
      request approval if needed → execute registry tool → return bounded result
      to the model → final response.
- [ ] Bound rounds, tool count, wall time, tokens, output bytes and recursion.
      Detect duplicate calls; support cancellation; preserve task/step/event
      traces. Never let the model change its own permissions.
- [ ] If tool calling is unsupported, malformed or not available after fallback,
      answer with an honest explanation or use deterministic routing for safe
      read-only tools. Never silently translate text into a shell command.
- [ ] Add evaluations for intents such as "open Spotify", "set volume to 20",
      "find my latest PDF", and adversarial requests embedded in webpages/files.

**Done when:** the model selects a typed allowlisted tool on local Ollama, policy
blocks a denied/destructive call, tool results return to the model, and the full
interaction is inspectable and bounded.

### Phase 4 — Reliable PC control and workflows

- [ ] Add approved file changes, app closing and explicit UI automation after
      the approval flow has proven reliable.
- [ ] Add undo/compensation where possible; show the before/after diff and exact
      target. No "undo" claim unless the inverse action completed.
- [ ] Add a small user-managed app/action allowlist UI and capability settings.
- [ ] Add local task queue/worker only when an action must outlive an HTTP
      request. Start with one heavy local inference; keep PC actions serialized
      where concurrent UI control would race.
- [x] Manual workflow runs (partial): a durable `queued` run is claimed by an
      in-process runner, executes model/transform/condition/delay nodes, records
      every node's real status and output, and audits the run. Unavailable node
      types are blocked, not faked.
- [ ] Add scheduled workflows only after worker durability, per-run approval
      policy, disable switch and audit retention exist. Schedules never bypass
      approval by running unattended. (Schedule triggers are saved but do not fire.)
- [ ] Add approval-gated connectors for `action.http`, notifications and
      project-task writes, bound to the exact payload at execution time.

### Phase 5 — Push-to-talk voice (not wake word yet)

- [ ] Push-to-talk button in the web app; explicit recording indicator, cancel,
      transcript preview/edit and permission state. Browser microphone access
      requires HTTPS or localhost and user permission.
- [ ] Local speech-to-text adapter. Benchmark `faster-whisper`/Whisper variants
      on this exact Windows CPU/GPU before choosing; make model size configurable.
- [ ] Local text-to-speech adapter (Piper candidate) with selectable voice,
      interrupt/stop and a text fallback. Keep generated audio local and do not
      upload recordings by default.
- [ ] Route transcript through the exact same orchestrator/tool policy as text.
      Voice never gets extra permissions. Read back approval prompts and require
      a clear UI confirmation; do not treat ambiguous speech as approval.
- [ ] Measure end-to-end latency, transcription error and resource use. Defer
      streaming/full duplex/LiveKit until push-to-talk works reliably.
- [ ] Wake word (e.g. openWakeWord) is a later opt-in: visible microphone state,
      local processing, false-positive tests, physical/software mute and no
      continuous recording retention.

**Done when:** a user holds push-to-talk, sees/corrects the transcript, triggers
a safe tool, hears the answer, can interrupt speech, and cannot approve a risky
action by ambiguous audio alone.

### Phase 6 — Memory and document knowledge

- [ ] Keep existing explicit memory CRUD/recall; add scopes, source and
      timestamps, user review/delete/export, and prompt-injection boundaries.
- [ ] Add the `nomic-embed-text` role through `model_gateway` and a typed embed
      contract; verify actual local embedding output/dimensions.
- [ ] Ingest user-selected files only, show the exact folder/files, respect
      exclusions, dedupe versions, chunk with citations and support delete/reindex.
- [ ] Start with local SQLite-compatible vector option only after evaluating
      current DB needs; use pgvector when there is a concrete requirement, not
      because a multi-user blueprint says so.
- [ ] Retrieval returns source snippets and file/page citations. No unsupported
      claims of "remembering everything"; let the user inspect what was indexed.

### Phase 7 — Proactive Jarvis (last, opt-in)

- [ ] Durable scheduler/worker, task history, missed-run handling and pause-all.
- [ ] User-configured morning briefing from real calendar/news/weather sources;
      show source, timestamp, stale/error state and timezone.
- [ ] Reminders, file watch and workflow triggers must have narrow scopes,
      dry-run previews, approval rules and a global disable switch.
- [ ] News, jobs, Planet and 3D visualization remain useful secondary modules,
      but do not take priority over PC safety, voice, memory and useful workflows.

## Explicitly defer

- Multi-user accounts, registration, tenant RLS and billing. Revisit only if
  multiple users or remote hosting become an actual requirement.
- Docker/WSL for the desktop executor (not supported as an interactive desktop
  control environment). Docker may still host optional DB/Redis services.
- LangGraph migration, microservices, LiveKit-first voice and OTel before a
  concrete need. Keep current deterministic orchestrator contracts until they
  block a tested capability.
- Always-on wake word, unrestricted shell, silent clipboard/screen capture,
  unattended destructive automation and access-control bypasses: prohibited or
  deferred indefinitely.

## Hardware and safety guardrails

1. One heavy Ollama generation at a time until measured otherwise; queue or
   reject competing heavy tasks rather than freezing the desktop.
2. Route routine control to the verified fast local role; use a reasoning model
   only when a task needs it. Make provider/model visible in task trace.
3. Measure RAM, model load, tool latency and UI responsiveness on this Windows
   machine. Never copy Linux-only `/proc` assumptions into Windows code.
4. Never fabricate battery, temperature, GPU utilization, file results,
   transcripts or action success.
5. The machine is the trust boundary: bind local-only, keep credentials server
   side, limit roots/apps, show every action, and put approvals in enforced code.
6. Use real Windows tests for desktop adapters; use mocks for unit tests and do
   not trigger real clicks, writes, audio or app launches in CI.

## First sprint (recommended)

1. Prove a real local Ollama chat/model trace.
2. Implement approval persistence + enforced execution gate + approve/reject UI.
3. Add Windows `get_system_status`, bounded `search_files`, `open_app` allowlist,
   `open_url`, and `set_volume`; screenshot behind explicit opt-in.
4. Add typed tool-call loop to the gateway/orchestrator and test it with local
   Ollama plus deterministic fixtures.
5. Demonstrate: "Open Spotify and set volume to 20" — ORBITO proposes the
   actions, executes only the allowed ones, and reports actual results.
6. Only then add push-to-talk, local STT/TTS, semantic file retrieval and
   proactive schedules.

Every phase ships a test, documentation update, and conventional commit. Push
after each coherent milestone when the configured remote is available.
